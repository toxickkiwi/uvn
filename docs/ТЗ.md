# ТЗ для Codex: CRM на Google Таблице и Apps Script

Oct 3, 2026 · @Tony

### 1. Задача

Нужно сделать внутреннее веб-приложение на Google Apps Script, которое даёт удобный интерфейс к Google Таблице. Таблица остаётся единственной базой данных. Это CRM для менеджера по продажам онлайн-школы «Учёт в народ» (курсы по бухгалтерии и налогам, продажи идут через GetCourse).

Пользователи:

- Менеджер, сейчас один. Ведёт 5–10 новых обращений в день, переписывается с клиентами в ВК, Инстаграме, Максе, Telegram, почте и чате GetCourse. Работает с компьютера, с телефона получает уведомления и иногда открывает карточки.

- Руководитель (Марина Фёдоровна). Смотрит отчёт. Справочники, цены и шаблоны правит прямо в таблице.

Что приложение должно решать:

- Каждый клиент — одна карточка, без дублей.

- У каждой открытой сделки всегда есть следующая задача с датой. Система показывает, кому писать сегодня, и присылает напоминание в Telegram.

- Сообщения клиентам готовятся из шаблонов с подстановкой имени и курса и копируются одной кнопкой.

- Руководитель видит три цифры за любой период: сколько было обращений, в каких каналах, какая конверсия в продажу.

Жёсткие ограничения:

- Только Google: таблица + Apps Script. Нет своего сервера, внешней базы, npm-сборки и платных сервисов.

- Переписка с клиентами в приложение не встраивается. Храним только ссылку на диалог, а для Инстаграма только ник.

- Звонков и телефонии нет.

- Названия листов и заголовки колонок — контракт. Код ищет колонки по заголовку, а не по номеру. Структуру не менять без согласования.

- Весь интерфейс на русском языке. Часовой пояс Europe/Moscow.

Что сдать:

- Исходный код проекта Apps Script в репозитории (структура — раздел 2).

- Функцию setupSpreadsheet(), которая создаёт недостающие листы, заголовки и выпадающие списки, не трогая существующие данные.

- README на русском: как привязать скрипт к таблице, опубликовать веб-приложение, подключить Telegram-бота и включить триггеры. Пишется для человека без опыта программирования.

- Функцию runSelfTests() с проверками бизнес-правил из раздела 4.

К ТЗ приложен файл CRM_стартовая_таблица.xlsx. В нём все листы с точными заголовками, справочники, тарифы, шаблоны и история обращений, перенесённая из старой таблицы. Этот файл загружается в Google Диск и открывается как Google Таблица — к ней и привязывается скрипт.

### 2. Стек и структура проекта

Скрипт привязан к таблице (container-bound) и публикуется как веб-приложение. Локальная разработка ведётся через clasp, код — обычный JavaScript для рантайма V8, без TypeScript и без сборки.

Фронтенд: одна страница из HtmlService. Vue 3 (global build) и SortableJS подключаются тегом <script> с cdn.jsdelivr.net с фиксированной версией. CSS свой, без фреймворков. Маршрутизация по хэшу: #today, #board, #deal/D001, #report, #templates.

Структура репозитория:

```
.clasp.json            # scriptId, rootDir: src
README.md              # инструкция по развёртыванию (рус.)
src/
  appsscript.json
  Main.gs              # doGet, include(), проверка доступа
  Db.gs                # чтение/запись листов по заголовкам, блокировки
  Rules.gs             # нормализация, валидация, переходы стадий
  Api.gs               # функции для google.script.run (раздел 5)
  Report.gs            # расчёт отчётов
  Telegram.gs          # отправка сообщений, сводки, напоминания
  Setup.gs             # setupSpreadsheet(), setupTriggers()
  Tests.gs             # runSelfTests()
  Index.html           # каркас страницы
  Styles.html          # CSS
  App.html             # Vue-приложение (можно разбить на App*.html)
```

appsscript.json:

```
{
  "timeZone": "Europe/Moscow",
  "runtimeVersion": "V8",
  "exceptionLogging": "STACKDRIVER",
  "webapp": {
    "executeAs": "USER_ACCESSING",
    "access": "ANYONE"
  },
  "oauthScopes": [
    "https://www.googleapis.com/auth/spreadsheets.currentonly",
    "https://www.googleapis.com/auth/script.external_request",
    "https://www.googleapis.com/auth/script.scriptapp",
    "https://www.googleapis.com/auth/userinfo.email"
  ]
}
```

executeAs: USER_ACCESSING нужен, чтобы Session.getActiveUser().getEmail() возвращал почту и для обычных аккаунтов Gmail. access: ANYONE означает любой вошедший Google-аккаунт; реальный доступ ограничивают права на таблицу и проверка по листу «Пользователи» (раздел 7). Если у школы окажется Google Workspace, достаточно сменить на DOMAIN.

Технические правила:

- Таблица открывается через SpreadsheetApp.getActive().

- Лист читается целиком один раз за вызов: getDataRange().getValues(). Колонки сопоставляются по заголовкам первой строки. Запись — setValues по строке, не по ячейке.

- Все записи выполняются под LockService.getScriptLock() с ожиданием до 10 секунд.

- Справочники, тарифы, шаблоны и настройки кэшируются в CacheService на 5 минут.

- Между сервером и клиентом даты передаются строками ISO 8601, потому что google.script.run не передаёт объекты Date. В таблицу записываются настоящие даты.

- Секреты (токен Telegram-бота) хранятся в PropertiesService.getScriptProperties(), а не в таблице.

- Любая серверная ошибка возвращается клиенту понятным русским текстом и показывается всплывающим сообщением.

### 4. Бизнес-правила

Все правила проверяются на сервере в Rules.gs. Клиент повторяет только простые проверки ради удобства.

4.1. Стадии. Открытые стадии: Новое, В диалоге, Курс подобран, Заказ создан, Отложено. Закрытые: Оплачено, Отказ. Переход возможен из любой стадии в любую, в том числе повторное открытие закрытой сделки.

| Стадия | Что обязательно при сохранении | Что делает система |
|---|---|---|
| Новое | Дата задачи | Если сделка в «Новое» дольше NEW_DEAL_ALERT_MIN минут, она подсвечивается красным |
| В диалоге, Курс подобран, Заказ создан | Дата задачи | — |
| Отложено | Дата задачи не раньше завтрашнего дня | В эту дату ежедневный триггер переводит сделку в «В диалоге» и ставит задачу «Вернуться к клиенту» |
| Оплачено | Сумма > 0, Способ оплаты, Дата оплаты (по умолчанию сегодня) | Очищает «Следующая задача» и «Дата задачи», очищает «Причина отказа» |
| Отказ | Причина отказа | Очищает задачу |

4.2. Задачи по умолчанию. Если менеджер не указал задачу сам, система подставляет:

| Событие | Следующая задача | Дата задачи |
|---|---|---|
| Создана сделка в потоке «Входящее» | Ответить клиенту | Сейчас |
| Создана сделка «Неоплаченный заказ» | Написать по заказу | Сейчас + 10 минут |
| Создана сделка «Реактивация» (клиент ответил на рассылку) | Написать повторно | Сегодня + FOLLOWUP_DAYS |
| Добавлено касание типа «Написал», «Отправил материалы» или «Шаблон» | Написать повторно | Сегодня + FOLLOWUP_DAYS, время TASK_DEFAULT_TIME |

Начальная стадия по потоку: Входящее → «Новое», Реактивация → «В диалоге», Неоплаченный заказ → «Заказ создан».

Если касание добавлено к сделке в стадии «Новое», сделка автоматически переходит в «В диалоге».

4.3. Журнал. Любая смена стадии автоматически пишет касание типа «Смена стадии» с текстом «Новое → В диалоге». Для «Отказ» в текст добавляется причина, для «Оплачено» — сумма. Копирование шаблона пишет касание типа «Шаблон» с текстом «Шаблон: <Название>».

4.4. Нормализация при сохранении клиента:

- Ник: убрать @ и пробелы, привести к нижнему регистру. Если вставлена ссылка instagram.com/<ник>/, извлечь ник.

- Телефон: оставить только цифры; 11 цифр с первой 8 → заменить 8 на 7; 10 цифр → добавить 7 в начало.

- Почта: trim и нижний регистр.

- Если в «Ссылка на диалог» вставлена ссылка вида …/user/control/user/update/id/<цифры>, заполнить «ID GetCourse».

4.5. Клиент без контакта не сохраняется. Нужно хотя бы одно поле из пяти: ник, ссылка на диалог, ID GetCourse, почта, телефон.

4.6. Дубли. Перед созданием клиента сервер ищет совпадения после нормализации: ник, ID GetCourse, почта, телефон — точное совпадение; ссылка на диалог — точное совпадение без https:// и завершающего /. Совпадение только по имени дублем не считается. Если что-то найдено, интерфейс показывает найденные карточки и две кнопки: «Это он — создать сделку для этого клиента» и «Это другой человек».

4.7. Сумма. При выборе курса и тарифа из подсказок «Сумма, ₽» подставляется из «Тарифы». Ручное значение не перезаписывается, пока менеджер сам не сменит тариф. Для комбо сумма вводится вручную.

4.8. Шаблоны. Подстановка переменных: {Имя} — «Клиенты».Имя; {Курс}, {Тариф}, {Сумма} — из сделки, сумма с разделителем тысяч и знаком ₽; {Менеджер} — «Пользователи».Имя текущего пользователя. Переменная без значения заменяется пустой строкой, а в предпросмотре такое место подсвечивается.

4.9. Даты. «Дата создания» не может быть в будущем. «Дата задачи» в прошлом допускается только для импортированных записей; при ручном сохранении интерфейс предупреждает, но не блокирует.

4.10. Удаление. Удалять клиентов, сделки и касания через интерфейс нельзя. Ошибочную сделку закрывают стадией «Отказ» с причиной «Другое».

### 5. Серверный API

Все функции в Api.gs вызываются через google.script.run. Каждая начинается с requireUser_() (раздел 7) и возвращает простой объект { ok: true, data } или { ok: false, error: 'Текст для пользователя', field?: 'имя поля' }. Исключения внутри перехватываются и превращаются в такой ответ. Имена полей в JSON — английские (camelCase), соответствие колонкам таблицы задаётся одной картой в Db.gs.

| Функция | Вход | Возвращает |
|---|---|---|
| getBootstrap() | — | Текущий пользователь (почта, имя, роль), справочники, активные тарифы, активные шаблоны, настройки, URL веб-приложения |
| getToday() | — | overdue: открытые сделки с датой задачи раньше сегодняшнего дня; today: с датой задачи сегодня; fresh: сделки «Новое» без касаний, кроме «Обращение»; counters: за сегодня создано сделок, добавлено касаний (без «Смена стадии»), оплачено сделок и их сумма |
| listDeals(filter) | { stages?, potok?, channel?, course?, from?, to?, query? }; query ищет по имени, нику, почте, телефону, ID | Массив сделок с полями клиента clientName, nick, dialogUrl |
| getDeal(id) | ID сделки | { deal, client, touches }, касания от новых к старым, плюс другие сделки этого клиента |
| findDuplicates(client) | Черновик клиента | Массив подходящих клиентов (правило 4.6) |
| createDeal(payload) | { clientId? , client?, deal }: либо существующий клиент, либо новый; force: true пропускает проверку дублей | { dealId, clientId }. Создаёт касание «Обращение» с текстом запроса |
| updateDeal(id, patch) | Изменённые поля сделки | Обновлённая сделка. Применяет правила 4.1–4.3 |
| updateClient(id, patch) | Изменённые поля клиента | Обновлённый клиент (правила 4.4–4.6, дубли исключая самого клиента) |
| addTouch(dealId, touch) | { type, text, nextTask?, nextTaskDate? } | Касание и обновлённая сделка (правило 4.2) |
| logTemplateUse(dealId, templateId) | — | Касание «Шаблон» и обновлённая сделка |
| markChecked(kind, id) | kind: client или deal | Очищает «Проверить» |
| getReport(from, to) | Даты ISO включительно | См. ниже |

getReport возвращает:

- leads — количество сделок с «Дата создания» в периоде;

- byChannel — то же количество по каналам;

- byPotok — по потокам;

- paidFromLeads — сколько из сделок периода сейчас в «Оплачено»;

- conversion — paidFromLeads / leads (0, если обращений нет);

- revenue — сумма «Сумма, ₽» по сделкам с «Дата оплаты» в периоде;

- byCourse — оплаты и выручка по курсам;

- lostReasons — количество отказов по причинам среди сделок периода;

- funnel — количество сделок периода по текущим стадиям.

Конверсия считается по когорте: из обращений, созданных в периоде, сколько уже оплачено. Выручка считается по дате оплаты. Обе цифры подписываются в интерфейсе так, чтобы разница была понятна.

### 6. Интерфейс

Приложение открывается на экране «Сегодня». Сверху постоянная панель: название, вкладки «Сегодня», «Воронка», «Шаблоны», «Отчёт» (вкладка «Отчёт» видна только роли «руководитель»), поле поиска и кнопка «+ Обращение». Горячие клавиши: N — новое обращение, / — поиск.

6.1. Сегодня (#today)

- Сверху счётчики дня: новых обращений, касаний, оплат и сумма.

- Три блока по порядку: «Просрочено» (красная метка), «На сегодня», «Без ответа» (fresh). Пустой блок показывает короткую строку «Всё сделано».

- Строка сделки: имя, канал (значок или короткая метка), курс, текст следующей задачи, время, сколько дней с последнего касания. Справа кнопка «Открыть диалог» (ссылка на диалог, для Инстаграма — https://instagram.com/<ник>) в новой вкладке. Клик по строке открывает карточку.

- Быстрые действия прямо в строке: «Написал» (добавляет касание и переносит задачу по правилу 4.2) и «+1 день».

6.2. Воронка (#board)

- Колонки — открытые стадии в порядке справочника; справа две свёрнутые колонки «Оплачено» и «Отказ» с количеством за выбранный период (по умолчанию текущий месяц).

- Карточка: имя, курс, сумма, дата задачи; просроченная дата выделена красным; пометка «Проверить» — жёлтой точкой.

- Перетаскивание карточки (SortableJS) меняет стадию через updateDeal. Если стадия требует полей (Оплачено, Отказ, Отложено), открывается маленькое окно с этими полями; при отмене карточка возвращается на место.

- Фильтры: поток, канал, курс, поиск.

- На экране уже 768 px вместо колонок показывается список с выбором стадии сверху.

6.3. Карточка сделки (#deal/D001) — три зоны, на телефоне идут друг под другом.

- Слева «Клиент»: имя, ник, ссылка на диалог, ID GetCourse (ссылка по GC_USER_URL), почта, телефон, другие сделки клиента. Поля редактируются по клику, сохраняются при уходе с поля.

- В центре «История»: поле добавления касания (выбор типа, текст, кнопка «Добавить», Ctrl+Enter) и лента касаний от новых к старым.

- Справа «Сделка»: стадия, поток, канал, курс и тариф с подсказками, сумма, способ оплаты, номер заказа, следующая задача и дата с кнопками «Сегодня», «+1 день», «+2 дня», «+1 неделя». Внизу крупные кнопки «Оплачено» и «Отказ».

- Панель «Шаблоны» открывается кнопкой в зоне истории: список по ситуациям, предпросмотр с подставленными значениями, кнопка «Скопировать». После копирования вызывается logTemplateUse и показывается подсказка «Скопировано».

- Если у клиента или сделки заполнено «Проверить», сверху жёлтая плашка с текстом и кнопкой «Проверено».

6.4. Новое обращение — модальное окно.

- Канал (кнопки), поток (по умолчанию «Входящее»).

- Контакт: одно поле, куда вставляется ник, ссылка, почта или телефон; тип определяется автоматически по правилу 4.4.

- Имя.

- Запрос клиента.

- Необязательно: курс и тариф.

При уходе с поля контакта вызывается findDuplicates, и найденные клиенты показываются под полем. «Сохранить» (Enter) создаёт сделку и открывает её карточку. Цель — заводить обращение меньше чем за 20 секунд.

6.5. Шаблоны (#templates) — список шаблонов по ситуациям с поиском и кнопкой «Скопировать» без подстановки. Редактирования в интерфейсе нет: шаблоны правятся в таблице.

6.6. Отчёт (#report)

- Выбор периода: «Эта неделя», «Прошлая неделя», «Этот месяц», «Прошлый месяц», свой период.

- Сверху три крупные цифры: обращения, конверсия в продажу, выручка.

- Ниже: столбчатая диаграмма обращений по каналам (простые CSS-полосы, без библиотек), таблица по курсам (оплаты, выручка), причины отказов, текущие стадии сделок периода.

- Кнопка «Скопировать как таблицу» копирует цифры в буфер в формате TSV.

6.7. Общие требования

- Шрифт системный, светлая тема, базовый размер 14 px, на телефоне 16 px.

- Каждое сохранение показывает индикатор; при ошибке поле подсвечивается, текст ошибки показывается всплывающим сообщением.

- После любой записи перечитываются только изменённые данные, а не вся страница.

- Даты отображаются как «03.10, 10:00», для текущего года без года.

- Состояние фильтров хранится в URL-хэше, чтобы ссылку можно было открыть повторно.

### 7. Доступ, уведомления, триггеры

7.1. Доступ. Защита двухслойная.

- Таблица расшарена с правом редактирования только сотрудникам. Так как веб-приложение выполняется от имени вошедшего пользователя, посторонний физически не может прочитать данные.

- requireUser_() берёт Session.getActiveUser().getEmail() и ищет активную строку в «Пользователи». Не нашёл — doGet отдаёт страницу «Нет доступа. Обратитесь к руководителю» с почтой, под которой человек вошёл; API-функции возвращают ошибку.

Роль «руководитель» видит всё и вкладку «Отчёт». Роль «менеджер» видит все сделки, но не отчёт.

7.2. Telegram-бот. Токен хранится в свойстве скрипта TELEGRAM_BOT_TOKEN. Сообщения отправляются через UrlFetchApp на https://api.telegram.org/bot<token>/sendMessage с parse_mode: HTML. Ошибка отправки пишется в лог и не ломает остальную работу. Каждое сообщение содержит ссылку на веб-приложение (ScriptApp.getService().getUrl()) с нужным хэшем.

| Уведомление | Когда | Кому | Содержание |
|---|---|---|---|
| Утренняя сводка | Ежедневно в DIGEST_HOUR | Каждому менеджеру по его сделкам | «Просрочено: N, на сегодня: N, без ответа: N» и ссылка на «Сегодня» |
| Напоминание о задаче | Когда наступила «Дата задачи» | Ответственному | Имя, курс, текст задачи, ссылка на карточку |
| Новое обращение без ответа | NEW_DEAL_ALERT_MIN минут в стадии «Новое» без касаний | Ответственному | Имя, канал, запрос, ссылка на карточку |
| Недельный отчёт | Понедельник, DIGEST_HOUR | Руководителю | Обращения, по каналам, конверсия, выручка за прошлую неделю |

Для подключения нужна вспомогательная функция telegramShowChatIds(). Сотрудник пишет боту /start, владелец запускает функцию, и она выводит в лог chat ID из getUpdates, которые затем вставляются в «Пользователи».

7.3. Триггеры. Создаются функцией setupTriggers() от имени владельца таблицы. Функция идемпотентна: сначала удаляет свои старые триггеры.

| Функция | Расписание | Что делает |
|---|---|---|
| cronEvery15m() | Каждые 15 минут | Напоминания о задачах с датой в интервале (последний запуск, сейчас]; уведомления о новых обращениях без ответа. Время последнего запуска хранится в свойствах скрипта, чтобы не слать повторно |
| cronDaily() | Ежедневно в DIGEST_HOUR | Переводит «Отложено» с наступившей датой в «В диалоге» (правило 4.1); отправляет утреннюю сводку; по понедельникам — недельный отчёт |

7.4. Меню в таблице. onOpen() добавляет меню «CRM» с пунктами «Открыть приложение», «Подготовить таблицу» (setupSpreadsheet), «Включить уведомления» (setupTriggers), «Показать chat ID Telegram», «Запустить самопроверку» (runSelfTests).

7.5. setupSpreadsheet(). Создаёт отсутствующие листы и недостающие колонки (добавляет в конец, существующие не трогает), закрепляет строку заголовков, ставит выпадающие списки из «Справочники» на колонки Поток, Канал, Стадия, Способ оплаты, Причина отказа, Тип, заполняет «Настройки» значениями по умолчанию для отсутствующих ключей. Повторный запуск ничего не ломает.

### 8. Этапы и критерии приёмки

Работать по этапам строго по порядку. Каждый этап заканчивается рабочим состоянием и коммитом. Следующий этап начинается только после того, как пройдены критерии текущего.

- Каркас и данные: appsscript.json, Db.gs, Setup.gs, меню, doGet с проверкой доступа.

- Правила и API: Rules.gs, Api.gs, Tests.gs.

- Основные экраны: «Сегодня», карточка сделки, новое обращение.

- Воронка и шаблоны.

- Отчёт.

- Telegram и триггеры.

- README и финальная проверка.

Критерии приёмки

Этап 1:

- ☐ На копии стартовой таблицы setupSpreadsheet() проходит без ошибок, при повторном запуске данные и порядок колонок не меняются.

- ☐ Пользователь из листа «Пользователи» открывает приложение; пользователь не из списка видит страницу «Нет доступа» со своей почтой.

Этап 2:

- ☐ runSelfTests() проверяет и проходит: нормализацию ника, телефона (8…, +7…, 10 цифр), почты; поиск дублей по каждому из пяти полей; отказ сохранить клиента без контакта; обязательные поля для «Оплачено», «Отказ», «Отложено», открытых стадий; задачи по умолчанию; авто-переход «Новое» → «В диалоге»; запись касания «Смена стадии»; подстановку переменных шаблона; формулы отчёта на тестовом наборе.

- ☐ Тесты работают на временных листах с префиксом TEST_ и удаляют их за собой.

Этап 3:

- ☐ На импортированных данных «Сегодня» показывает просроченные сделки из старой таблицы.

- ☐ Новое обращение по нику, который уже есть в базе, показывает существующего клиента.

- ☐ Кнопка «Написал» добавляет касание и переносит задачу на FOLLOWUP_DAYS.

- ☐ Все экраны работают на ширине 375 px.

Этап 4:

- ☐ Перетаскивание в «Отказ» без причины невозможно; после отмены карточка возвращается назад.

- ☐ Копирование шаблона кладёт в буфер текст с подставленным именем и пишет касание.

Этап 5:

- ☐ Цифры отчёта за сентябрь–октябрь 2026 совпадают с ручным подсчётом по листу «Сделки».

- ☐ Менеджер не видит вкладку «Отчёт», и getReport возвращает ему ошибку.

Этап 6:

- ☐ Утренняя сводка и напоминание о задаче приходят в Telegram; одно и то же напоминание не приходит дважды.

- ☐ Сделка «Отложено» с сегодняшней датой после cronDaily() оказывается в «В диалоге» с задачей.

Этап 7:

- ☐ Человек без опыта по README за 30 минут разворачивает приложение на чистой копии таблицы.

- ☐ При 2 000 сделок и 10 000 касаний экран «Сегодня» загружается быстрее 5 секунд.

### 9. Вне рамок и открытые вопросы

Не делать в этой версии:

- Интеграцию с GetCourse (webhook doPost, автосоздание сделок по заказам). Код писать так, чтобы потом можно было добавить doPost, который вызывает ту же логику, что createDeal и updateDeal.

- Кампании реактивации: загрузку списков выпускников и массовые задачи.

- Встраивание переписки из мессенджеров.

- Редактирование справочников, шаблонов и пользователей через интерфейс — это делается в таблице.

- Распределение обращений между несколькими менеджерами (поле «Ответственный» уже есть).

- Удаление записей.

Открытые вопросы. Пока ответа нет, применяется поведение по умолчанию, указанное в скобках.

- ☐ Формат ссылки на заказ в GetCourse (номер показывается без ссылки, GC_ORDER_URL пуст).

- ☐ Google Workspace со своим доменом или обычные Gmail (access: ANYONE + проверка по листу «Пользователи»).

- ☐ Цены комбо и конспектов (вводятся вручную).

- ☐ Считать ли задаток 5 000 ₽ продажей (нет: продажа — только стадия «Оплачено»).

Если по ходу работы найдётся противоречие в ТЗ или правило, которое нельзя реализовать на Apps Script, не придумывать своё решение молча: описать проблему и предложенный вариант в README в разделе «Отклонения от ТЗ».
